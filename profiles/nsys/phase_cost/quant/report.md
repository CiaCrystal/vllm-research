# Qwen3-0.6B：bf16 与量化方案对比（非 eager）

日期：2026-11-06。环境：RTX 5070（SM120），WSL2。源码未改动。基线报告：`../noneager/report.md`。

**测量范围按用户要求缩减：** 只用 nsys，配置只测 A、D、F，总时长控制在 1 小时内（实际 33 分钟，不含报告）。因此不是原任务的完整矩阵，差异见第 6 节。

## 结论

| 问题 | 结论 |
| ---- | ---- |
| 能跑通 | FP8、MXFP8、INT8（Triton，自转 checkpoint）跑通，且 112 个线性层都确认已量化。MXFP4 启动失败 |
| 请求耗时 | FP8 和 INT8 在三个配置下都更快。FP8：A −11%～−16%，D −20%～−25%，F 约 −23%。INT8：A −6%～−11%，D −27%～−31%，F 约 −19% |
| MXFP8 | 只有 D 变快（−11%～−17%）。A 变慢（+13%～+20%），F 与 bf16 差异在噪声内 |
| 变化来源 | 收益全部来自线性层。Prefill 线性层 FP8 降 39%～47%，MXFP8、INT8 大批量下降 54%～62%。Decode 线性层 FP8、INT8 降 35%～46%，MXFP8 在批大小 1 时反而慢 16%～18%。注意力计算没有变化 |
| 激活量化 | INT8 抵消线性层节省的 10%～19%。FP8 约 2%～8%，且融合在 Triton kernel 里，拆不干净。MXFP8 在 F 抵消约 59% |
| TTFT、TPOT | TPOT：FP8 −12%～−22%，INT8 −14%～−21%，MXFP8 +1%～+18%。TTFT：D 降 29%～42%，F 上 FP8、INT8 降 27%～36%，MXFP8 在噪声边界。A 的 TTFT 不下结论。详见第 8 节 |
| 显存 | 模型从 1.12 GiB 降到 0.71～0.73 GiB（约 −35%），KV 容量增加 7%～13% |
| 精度 | GSM8K（1319 题）：bf16 39.0%、39.6%，FP8 37.8%，MXFP8 37.0%，INT8 36.6%。多重比较校正后都不显著。INT8 触顶 256 token 的回答增至约 3 倍 |

## 1. 路线可用性

| 路线 | 跑通 | 线性 kernel | 量化生效的依据 | 启动 |
| ---- | ---- | ----------- | -------------- | ---- |
| bf16 | 是 | `Kernel2`（CUTLASS GEMM）、`kernel`（cuBLAS gemvx） | 基线 | 引擎初始化 7 s |
| FP8 `fp8_per_tensor` | 是 | 日志 `Selected CutlassFP8ScaledMMLinearKernel`；trace 中是 SM120 的 CUTLASS `device_kernel` | 每 step 恰好 112 个 `device_kernel`，无 bf16 GEMM/GEMV；模型 1.12→0.71 GiB | 7 s |
| MXFP8 `mxfp8` | 是 | 日志没有 `Selected` 行；trace 中是 `DeviceGemmMxfp8GemmSm120` | 日志 `Quantizing 112 layers ... (from linear: mxfp8)`；每 step 112 个 MXFP8 GEMM；模型 0.73 GiB | autotune 293 s |
| MXFP4 `mxfp4` | **否** | 无 | 权重已量化（112 层，0.54 GiB），首次前向失败 | 失败 |
| INT8 Triton | 是 | 日志 `Selected TritonInt8ScaledMMLinearKernel`；trace 中是 `scaled_mm_kernel` | 每 step 112 个 `scaled_mm_kernel`；模型 0.72 GiB | 8 s |

冒烟：bf16、FP8、INT8 和关闭 autotune 的 MXFP8 各发 4 个请求（1 个预热加 3 个正式），全部返回 200，usage 正确。默认 autotune 的 MXFP8 在不带 nsys 时同样通过。所有路线 JIT warmup 均为 0.00 s，Graph capturing 3～8 s，日志正常，CUDA Graph 捕获未受量化影响（A 的 Prefill 仍是 29 个 Graph）。

`lm_head` 在所有路线都保持 bf16，trace 里每次采样仍有一个 gemvx。它在 `Step/*` 之外，已排除在线性层统计之外。

**MXFP4 失败原因：**

```text

flashinfer/utils.py:1567 wrapper -> _is_problem_size_supported
flashinfer/gemm/gemm_base.py:7990 _cute_dsl_gemm_fp4_requirement
flashinfer/gemm/kernels/sm12x_cute/runner.py:70 check_requirement

```

失败发生在 `determine_available_memory` → `profile_run`。完整日志：`smoke/mxfp4.serve.log`。按要求跳过，未尝试其他 `--linear-backend`。

**INT8 checkpoint：** `/home/bca/models/qwen3-0.6b-int8-w8a8-dynamic/`，用 `compressed_tensors` 的 `W8A8` 预设（权重 int8、对称、per-channel，激活动态 per-token）。196 个权重张量已量化，相对 L2 误差最大 1.2%，`lm_head` 忽略。文件 1.40→0.99 GiB。

- F 的请求中 Decode 占绝大多数（bf16 周期合计约 455 ms，Prefill 约 32 ms）。MXFP8 在 Prefill 省下约 15 ms，Decode 没有收益，所以整体在噪声内。

## 7. 解读注意

- **离散抬升：** 单个 kernel 或多个 step 会出现约 0.25～0.28 ms 的离散抬升，各路线都有。例子：D 的 bf16 Decode 线性时间分布是 1.86 和 2.11 ms 两档；FP8 的注意力计算 p5 为 1.827 ms，中位数 2.087 ms；`lm_head` 在 477 和 762 µs 两档。中位数落在哪一档会影响结果，所以线性层用四类中位数之和，不用总和的中位数。原因未确认。
- **GPU 忙时：** Decode 周期里 GPU 空闲约 0.09 ms，所有路线相同，所以周期变化都来自 GPU kernel。
- **单次矩阵乘数据不能外推：** 本次 FP8 的线性合计是 bf16 的 0.53～0.64 倍，这是模型运行测得的，不是从单次矩阵乘推出的。
- **差异小于约 5% 视为噪声。** FP8 和 INT8 之间，A、F 相差约 5%，不下谁更快的结论。D 中 INT8 快约 10%，但只有 1 次运行。

## 8. TTFT 和 TPOT

**计算方法：** 这次的请求不是流式，客户端没有直接测到 TTFT，所以数值都由 nsys trace 算出，是引擎侧数值。每个 token 的就绪时刻取该 step 之后采样 kernel（`reduce_kernel`、`_gumbel_sample_kernel`）在 GPU 上结束的时间。

- TTFT = 第 1 个 token 就绪 − Prefill `Step` 开始。
- TPOT = (最后一个 token 就绪 − 第 1 个 token 就绪) / (max_tokens − 1)。
- 批大小 8 时，8 个请求在同一批内，TTFT 和 TPOT 相同，TPOT 是每条请求的值，不是批次吞吐。

取窗口内 5 次的中位数，百分比是相对首尾两次 bf16 的范围。

| 配置 | 指标 | bf16 首 / 尾 | FP8 | MXFP8（关 autotune） | INT8 |
| ---- | ---- | ------------ | --- | -------------------- | ---- |
| A | TTFT（ms） | 6.37 / 8.98 | 10.92 | 10.08 | 10.00 |
| A | TPOT（ms） | 2.854 / 2.932 | 2.348（−18%～−20%） | 3.370（+15%～+18%） | 2.459（−14%～−16%） |
| D | TTFT（ms） | 159.42 / 149.18 | 105.21（−29%～−34%） | 100.76（−32%～−37%） | 91.87（−38%～−42%） |
| D | TPOT（ms） | 5.052 / 4.715 | 4.165（−12%～−18%） | 5.146（+2%～+9%） | 3.970（−16%～−21%） |
| F | TTFT（ms） | 34.26 / 34.59 | 22.10（−36%） | 32.60（−5%～−6%） | 24.99（−27%～−28%） |
| F | TPOT（ms） | 3.598 / 3.616 | 2.803（−22%） | 3.646（+1%） | 2.953（−18%） |

**核对：** 引擎侧总耗时比客户端请求耗时少 4.5～7.4 ms，15 个运行都在这个范围。这部分是 HTTP、调度和进程间通信，所以客户端看到的 TTFT 最多再加这么多。TPOT 和 Decode 周期相差不超过 2%。

**TTFT 的两种情况：**

| 情况 | 配置 | GPU 跨度和 CPU 时间 | 对 TTFT 的影响 |
| ---- | ---- | ------------------- | -------------- |
| GPU 受限 | D 全部路线，F 的 bf16、FP8 | 跨度明显大于 `Step` CPU 时间，接近 kernel 时间 | kernel 变快能直接降低 TTFT |
| CPU 受限 | A 全部路线，F 的 MXFP8、INT8 | 跨度基本等于 `Step` CPU 时间，量化路线明显大于 kernel 时间 | GPU 在等 CPU 发射，kernel 变快不再降低 TTFT |

Prefill 的 `Step` CPU 时间、GPU 跨度和 kernel 时间（ms）：

| 配置 | bf16 首 / 尾 | FP8 | MXFP8 | INT8 |
| ---- | ------------ | --- | ----- | ---- |
| A | 4.84 / 7.66、5.53 / 8.08、4.72 / 4.49 | 10.17、9.68、3.10 | 9.17、8.74、2.79 | 9.25、8.81、3.39 |
| D | 9.97 / 11.78、158.41 / 148.21、157.40 / 147.35 | 15.05、104.15、103.28 | 55.58、99.61、97.87 | 22.30、90.86、89.64 |
| F | 11.07 / 10.10、33.30 / 33.44、32.34 / 32.57 | 14.86、21.03、19.94 | 31.83、31.41、16.86 | 24.09、23.60、17.45 |

**限制：**

- **A 的 TTFT 不下结论。** 首尾两次 bf16 就差 41%，单次范围重叠（bf16 6.2～12.2 ms，FP8 8.1～14.6 ms，MXFP8 9.5～13.5 ms，INT8 9.2～11.7 ms）。量化路线的中位数更高，但这里的 kernel 时间都更低。
- **CPU 受限配置的 TTFT 可能被 nsys 放大。** 这部分取决于 CPU 发射，而 CUPTI 增加 CPU 开销，这一点没有单独量化，也没有不带 nsys 的对照。
- **F 的 INT8 单次范围大**（20.9～35.1 ms），MXFP8 也有 32.0～38.3 ms。5 次中位数只能看方向。
- **没有客户端流式测量。** MXFP8 是关闭 autotune 的数据，默认配置的 TTFT、TPOT 未测。
- **量化路线 Prefill CPU 时间增加的原因未分析。** MXFP8 在 D 为 55.6 ms，bf16 约 10～12 ms。
