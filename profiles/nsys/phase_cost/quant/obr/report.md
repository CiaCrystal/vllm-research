# OBR 精度复现与 2:4 稀疏 kernel（Qwen3-0.6B）

日期：2026-11-07。环境：RTX 5070（SM120），WSL2，非 eager。
参考文章：Guo、Li、Benini，*Optimal Brain Restoration for Joint Quantization and Sparsification of LLMs*，ICLR 2026，[arXiv:2509.11177](https://arxiv.org/abs/2509.11177)。

## 结论

| 问题 | 结论 |
| ---- | ---- |
| OBR 保得住多少精度 | **困惑度保住了一部分，GSM8K 保不住。** 非结构化 50%：困惑度 16.51→19.57，GSM8K 39%→2.1%。2:4：困惑度→30.92，GSM8K→1.4% |
| 稀疏 kernel 能跑吗 | **能。** 已接入 vLLM，用 `--linear-backend cutlass_sparse` 开启，数值验证通过 |
| 提速在哪里 | **只在 TTFT。** 同一 checkpoint 比稠密 FP8 kernel：TTFT −19%～−28%，整体耗时 −2%～−12%，TPOT 在噪声内 |
| 是否达到论文提速 | **没有。** 论文的 5.9 倍是相对 FP16 稠密 GEMM。这里 8192 token、权重 6144×1024 时，相对 bf16 约 3.3 倍（基线来自 CHG-007，批次不同），相对稠密 FP8 约 1.8 倍。端到端整体耗时相对稠密 FP8 只有约 1.1 倍 |
| 省显存吗 | **按现有指标没有。** 模型 0.72→0.77 GiB，KV 容量 −1.3%。原因未确认 |
| 能不能用 | **这个模型上不能。** 2:4 稀疏后 GSM8K 只有约 1.4%～1.7%，这个 kernel 目前只有测量价值 |

硬件上没有 INT4 的稀疏 Tensor Core，所以实现的是 **2:4 + FP8**，不是任务名里的 2:4 + INT4。

## 精度

校准：128 条 WikiText2，每条 2048 token，和论文一致。GSM8K 是全部 1319 题。困惑度是 WikiText2 test 上的 64 条 2048 token 片段，只量化权重，激活保持浮点。

| 方案 | GSM8K | 困惑度 | 触顶 256 token |
| ---- | ----- | ------ | ------------ |
| bf16 | 39.04% / 39.58% | 16.51 | 41 / 35 |
| FP8 稠密（对照） | 38.59% | 16.65 | 52 |
| INT8 稠密 | 36.62% | 16.56 | 123 |
| INT8 + 2:4，无补偿 | 0.99% | 93.84 | |
| FP8 + 2:4，无补偿 | 0.99% | 未测 | |
| INT8 + 2:4，OBR | 1.74% | 37.65 | |
| INT4 + 2:4，OBR | 0.91% | 69.59 | |
| FP8 + 2:4，OBR | 1.14% | 37.46 | |
| FP8 + 2:4，OBR + 级联校准 | 1.36% | 30.92 | 1094 |
| FP8 + 2:4 只剪 FFN，OBR + 级联校准 | 2.73% | 22.32 | 276 |
| FP8 + 非结构化 50%，OBR + 级联校准 | 2.12% | 19.57 | 200 |

- **补偿确实生效：** 2:4 的困惑度从 93.84 降到 30.92，单层相对误差目标约减半。
- **对照通过：** 同一流程不剪枝时是 38.59%，说明精度下降来自剪枝，不是 checkpoint 或加载路径的问题。
- **排除了 vLLM 路径问题：** 用 HF 和浮点激活跑前 160 题：bf16 40.0%，稠密 FP8 43.75%，非结构化 OBR 2.5%，2:4 OBR 2.5%，和 vLLM 一致。
- **表现：** 剪枝后的回答是通顺的句子，但算式错误，例如 `$<<3+4+16=...=20>>20`。这和困惑度只小幅上升吻合：一般文本还能预测，算术能力没了。

**和论文的差异：**

- 没有做权重旋转，因为这需要改激活路径。
- 是 W8A8（或 W4A8）、KV 不量化，不是 W4A4KV4。
- 论文没有测 GSM8K，它测的是常识类任务和困惑度，所以两边不能直接比较。论文报告的 Qwen2.5-1.5B 也比这里的 0.6B 大。
- 级联校准是我加的，论文的代码是否这样做未确认。
- 这是按论文公式独立重写的代码，不是官方实现，没有在论文的模型上验证过。

## 2:4 稀疏 kernel

**实现：** CUTLASS 自带 SM120 的稀疏 FP8 MMA（`mma.sync.aligned.kind::f8f6f4.sp::ordered_metadata.m16n8k64`），稠密是 k32，稀疏是 k64。权重作为 A 操作数，运行时把 `[K, N]` 权重压缩成 `[N, K/2]` 加元数据。

| 文件 | 内容 |
| ---- | ---- |
| `csrc/quantization/w8a8/cutlass/c3x/sparse_fp8_mm_sm120.cu` | CUTLASS kernel，C 接口 |
| `tools/build_sparse_fp8_sm120.sh` | 用 `.venv` 里的 nvcc 和 CUTLASS 编译 |
| `vllm/model_executor/kernels/linear/scaled_mm/cutlass_sparse.py` | 压缩、custom op、linear kernel |
| `vllm/model_executor/kernels/linear/__init__.py`、`vllm/config/kernel.py` | 注册 `cutlass_sparse` backend，默认选择不受影响 |

**数值验证：** 5 种形状、批量和单值 token scale，和浮点参考的相对误差都是 0.17%（bf16 舍入水平）。非 2:4 的权重在加载时报错。端到端的 GSM8K 是 1.67%，同一 checkpoint 的稠密 kernel 是 1.36%，差异在非确定性范围内。

### 微基准（µs，空闲 GPU，200 次中位数）

相对 vLLM 现有的稠密 FP8 路径（`cutlass_scaled_mm`），同形状。权重 2:4，随机数据。

| 权重形状 | 1 | 8 | 32 | 64 | 256 | 1024 | 2048 | 8192 token |
| -------- | - | - | -- | -- | --- | ---- | ---- | ---------- |
| 6144×1024 | 0.84 | 1.20 | 0.86 | 1.01 | 0.67 | 0.48 | 0.56 | 0.56 |
| 4096×1024 | 0.90 | 0.31 | 1.72 | 1.11 | 1.01 | 0.75 | 0.53 | 0.56 |
| 1024×2048 | 0.74 | 0.90 | 0.57 | 0.87 | 0.64 | 0.52 | 0.53 | 0.49 |
| 1024×3072 | 0.83 | 0.66 | 1.45 | 1.32 | 0.68 | 0.50 | 0.41 | 0.53 |

≥1024 token 时约为 0.41～0.75 倍，也就是约 1.3～2.4 倍提速。256 token 以下全部在 0.31～1.72 之间跳动，这时单次耗时只有 25～50 µs，时间主要在启动，不下结论。

### 端到端（流式，不带 nsys，2 轮，每组合 15 次）

同一个 checkpoint（`fp8_seq_all`）分别跑两种 kernel，两个数值分别是第 1、2 轮的中位数。单位 ms。

| 配置 | 指标 | bf16 | FP8 稠密 kernel | FP8 稀疏 kernel | 稀疏 vs 稠密 | 稀疏 vs bf16 |
| ---- | ---- | ---- | --------------- | --------------- | ------------ | ------------ |
| A 256×1 | TTFT | 10.48 / 12.12 | 12.56 / 12.53 | 9.81 / 9.03 | −22% / −28% | −6% / −26% |
| A | TPOT | 2.65 / 2.73 | 2.18 / 2.17 | 2.14 / 2.19 | −2% / +1% | −19% / −20% |
| A | 整体 | 95.85 / 99.20 | 82.08 / 81.82 | 78.46 / 79.35 | −4% / −3% | −18% / −20% |
| D 1024×8 | TTFT | 157.99 / 163.82 | 105.40 / 106.93 | 84.50 / 83.14 | −20% / −22% | −47% / −49% |
| D | TPOT | 4.61 / 4.75 | 3.79 / 3.83 | 3.75 / 3.75 | −1% / −2% | −19% / −21% |
| D | 整体 | 306.32 / 316.23 | 226.31 / 230.17 | 204.01 / 203.06 | −10% / −12% | −33% / −36% |
| F 256×8，129 | TTFT | 40.56 / 41.23 | 27.84 / 29.36 | 22.52 / 22.10 | −19% / −25% | −44% / −46% |
| F | TPOT | 3.66 / 3.71 | 2.83 / 2.88 | 2.80 / 2.79 | −1% / −3% | −23% / −25% |
| F | 整体 | 509.16 / 516.04 | 389.46 / 397.95 | 380.66 / 378.56 | −2% / −5% | −25% / −27% |

- **TTFT 明显下降：** 三个配置都超过噪声。A 的结果值得注意：之前稠密量化在 A 上没有 TTFT 收益（GPU 在等 CPU 发射），而稀疏 kernel 有。原因未分析，可能和 256 token 下的启动开销有关，但这是推测。
- **TPOT 没有变化：** Decode 的 M 只有 1 或 8，这和微基准一致。
- **整体耗时取决于 Prefill 占比：** D 的 Prefill 占比大，下降 10%～12%。F 是 129 token，下降 2%～5%，接近噪声。
- **表里“稀疏 vs bf16”的 TPOT 收益来自 FP8 本身**，不是稀疏。
- **同一 checkpoint 上稠密 kernel 不受零影响：** `fp8_seq_all` 和不剪枝的 `fp8_seq_none` 差异在噪声内，再次确认稠密路径不会因为零变快。

### 显存

| 路线 | `Model loading took` | `GPU KV cache size` |
| ---- | -------------------- | ------------------- |
| FP8 稠密 kernel | 0.72 GiB | 39,424 tokens |
| FP8 稀疏 kernel | 0.77 GiB | 38,912 tokens |

权重压缩了一半，但这两个指标没有下降。压缩时新旧权重同时存在，而这个数值可能包含峰值或分配器缓存，这是推测，加载后的实际占用没有单独测量。

## 限制与未做

- **模型不可用：** 这是核心限制，2:4 稀疏后的 Qwen3-0.6B 无法回答 GSM8K，kernel 的提速目前没有实用价值。
- **没有 INT4：** SM120 的稀疏 MMA 是 FP8/FP6/FP4，没有整数格式。E2M1（FP4）和 FP6 未测试，INT4 精度是用 INT8 kernel 模拟的。
- **只支持：** SM120、FP8、bf16 输出、per-channel 权重、K 为 128 的倍数、M ≥ 128、无 bias。
- **构建系统未接入 CMake：** 环境没有 `cmake` 且不能安装，所以用独立脚本编译出 `vllm/_sparse_fp8_sm120.so`，加载时用 `ctypes`。这个 `.so` 被 `.gitignore` 忽略，换机器要重新编译。
- **编译时关闭了 CCCL 版本检查：** `.venv` 的 nvcc 是 13.5，CUDA 头文件是 13.2，用了 `CCCL_DISABLE_CTK_COMPATIBILITY_CHECK`。
- **架构：** 用 `sm_120a` 编译，只验证了 RTX 5070。
- **未运行：** `ruff`、`pre-commit`、`pytest`（都不在 `.venv`），也没有写进仓库测试。数值验证脚本在 `/home/bca/models/obr/scripts/unit.py`。
- **耗时测量是 2 轮**，A 的 TTFT 单次波动较大。
- **论文的 5.9 倍未复现：** 硬件、基线和 kernel 都不同，且 INT4 无法在这张卡上验证。
