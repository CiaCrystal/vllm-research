# OBR 2:4 稀疏 kernel 验证（Qwen3-8B，RTX 3090）

日期：2026-11-07。参考文章：Guo、Li、Benini，*Optimal Brain Restoration for Joint Quantization and Sparsification of LLMs*，ICLR 2026，[arXiv:2509.11177](https://arxiv.org/abs/2509.11177)。

## 结论

| 问题 | 结论 |
| ---- | ---- |
| 换校准数据能挽回多少 | **大部分。** 改用模型自生成的 GSM8K 训练题解答做校准，INT8 + 2:4 + OBR 到 81.20%（−7.35 个百分点），INT4 到 69.90%；代价是 WikiText 困惑度 21.24。混合一半 WikiText 后为 77.41%、困惑度 12.85，两头兼顾。仍未达到 5 个百分点的标准，见“自生成校准”一节 |
| 2:4 + OBR 的 GSM8K 保得住吗（WikiText 校准） | **保住约一半。** bf16 88.55%，稠密 INT8 88.25%，INT8 + 2:4 + OBR 44.43%（稀疏 kernel 45.49%），INT4 + 2:4 + OBR 19.56%，无补偿 1.82%。未达到“下降不超过 5 个百分点”的标准 |
| 稠密 INT8 能用吗 | **能。** GSM8K 只掉 0.30 个百分点，困惑度不变，整体耗时快 1.65～2.01 倍 |
| 稀疏 kernel 能跑吗 | **能。** 在 sm_86 上编译运行，数值验证通过，已接入 vLLM |
| 稀疏 kernel 比稠密 INT8 快多少 | 同一 checkpoint 端到端：整体 1.07～1.15 倍，TPOT 1.10～1.16 倍，TTFT 无明显收益。微观上 ≥1024 token 线性部分 1.02～1.08 倍，**未达到 1.3 倍的标准** |
| 精度损失多少 | INT8 + 2:4 + OBR：GSM8K −44.1 个百分点，困惑度 9.14→11.97。INT4 + 2:4 + OBR：−69.0 个百分点，困惑度 14.14 |
| 2:4 + INT4 相对 bf16 快多少 | 目前的 INT4 只是以 s8 存放的权重，走 INT8 kernel，速度等于 INT8。它和稀疏 kernel 的组合没有单独测，同类的 INT8 + 稀疏为整体 1.84～2.17 倍 |
| 是否达到论文量级 | **没有。** 论文的 5.9 倍是 A100 上 INT4 kernel 相对 FP16 稠密 GEMM。这里 8192 token 的 INT8 稀疏 GEMM 相对 bf16 约 3.2 倍（`sparse_col`），且真正的 s4 × s4 kernel 未实现。两者不是同一个量 |

## 更正：第一版 OBR 的符号错误

第一版 `obr_8b.py` 把剪掉部分的误差写成 `+w`，应为 `-w`，所以第一步补偿方向相反，把误差放大了。当时的 OBR 结果（GSM8K 0.83%，困惑度 1749，比无补偿更差）全部作废，移到 `eval_signbug/`。

查明过程：

1. 反量化成 bf16、激活保持浮点后，OBR 困惑度 1538，仍差于无补偿的 269，说明问题不在激活量化。
2. 逐层测输出误差（`scripts/obr_diag.py`）：校准文本和留出文本的误差几乎相同，不是过拟合。权重范数比 0.89～0.97，削顶 0.03%，不是数值爆炸。但即使在校准文本上，OBR 的误差也比无补偿大，例如第 11 块 `o_proj` 0.321 对 0.145。
3. 回查代码发现符号错误。之前的 Cholesky 对比用的是同一个错误的误差向量，所以没有暴露问题。

修复后脚本在 `--check` 下用真实误差断言补偿有效。第 1 块补偿后的误差是只剪枝的 23%～44%，单层平均误差从 0.100 降到 0.010。

## 精度

全部在 `vllm serve` 内测量：公共参数，GSM8K 全部 1319 题（`tests/evals/gsm8k/gsm8k_eval.py`），困惑度是 WikiText2 test 上 64 段、每段 2047 token，用 `prompt_logprobs` 计算，激活走真实量化路径。

| 方案 | kernel | GSM8K | 答对 | 困惑度 | 触顶 256 token |
| ---- | ---- | ----- | ---- | ------ | ------------ |
| bf16 | | 88.55% | 1168 | 9.14 | 41 |
| INT8 稠密 | 稠密 INT8 | 88.25% | 1164 | 9.13 | 46 |
| INT8 + 2:4，无补偿 | 稠密 INT8 | 1.82% | 24 | 748.0 | 1319 |
| INT8 + 2:4，OBR | 稠密 INT8 | **44.43%** | 586 | **11.97** | 150 |
| INT8 + 2:4，OBR | 稀疏 INT8 | **45.49%** | 600 | **11.99** | 155 |
| INT4 + 2:4，OBR | 稠密 INT8 | 19.56% | 258 | 14.14 | 385 |

无补偿权重反量化成 bf16、激活保持浮点时，困惑度是 269.5。这说明无补偿的损失主要来自剪枝，不是激活量化。

- **对照通过：** bf16 和 INT8 的 88% 和 9 说明评测路径和困惑度计算可信。
- **精度下降来自 2:4 剪枝：** 同样的量化不剪枝几乎无损。
- **OBR 补偿很关键：** 无补偿只有 1.82%，所有回答都循环到 token 上限；OBR 回到 44.43%，困惑度 11.97 接近 bf16 的 9.14。
- **8B 比 0.6B 能保住更多：** 0.6B 上 2:4 + OBR 只有约 1.4%（当时 bf16 约 39%）。这次 8B 保住了约一半，但两次的评测路径不同（0.6B 是浮点激活），不能直接按比例比较。
- **困惑度保住不代表算术能力保住（坑 39）：** 困惑度只升 31%，GSM8K 却掉了一半。
- **INT4 损失更大：** 19.56%，困惑度 14.14。它和 INT8 共用掩码和级联链，所以可能略保守。
- **稀疏 kernel 在真实权重上和稠密一致：** 同一 checkpoint 的困惑度 11.97 对 11.99，GSM8K 586 对 600 题，差异在非确定性范围内（坑 31）。

## 自生成校准

依据是 RESP（arXiv:2512.02185，实验模型包括 Qwen3-8B）和 SSGR（arXiv:2511.18864）：推理任务的剪枝应使用推理数据，最好是模型自己生成的数据。

做法：bf16 Qwen3-8B 用 GSM8K 评测的格式（`train[:5]` 作为 5 道例题，贪心，最多 256 token），在 vLLM 里解答训练集 `train[5:1205]`。每个 2048 token 的窗口以这 5 道例题开头，后面接生成的“题目 + 解答”，共 128 个窗口。其余设置和 WikiText 校准完全相同。脚本是 `scripts/gen_calib.py`，生成耗时 7 分钟，OBR 22 分钟。

| 方案 | 校准数据 | GSM8K | 答对 | WikiText 困惑度 |
| ---- | ---- | ---- | ---- | ---- |
| bf16 | | 88.55% | 1168 | 9.14 |
| INT8 + 2:4 + OBR | WikiText | 44.43% | 586 | 11.97 |
| INT8 + 2:4 + OBR | **自生成 GSM8K** | **81.20%** | 1071 | 21.24 |
| INT4 + 2:4 + OBR | WikiText | 19.56% | 258 | 14.14 |
| INT4 + 2:4 + OBR | **自生成 GSM8K** | **69.90%** | 922 | 28.29 |
| INT8 + 2:4 + OBR | **混合（各 64 窗口）** | **77.41%** | 1021 | **12.85** |
| INT4 + 2:4 + OBR | **混合（各 64 窗口）** | **63.38%** | 836 | **15.14** |

- **校准数据是主要矛盾：** 同样的掩码方法和补偿，只换数据，GSM8K 提升 36.8 个百分点（INT8）和 50.3 个百分点（INT4）。
- **有取舍：** WikiText 困惑度从 11.97 升到 21.24。补偿保住的是校准数据代表的能力。
- **混合能兼顾：** 一半 WikiText、一半自生成时，困惑度 12.85 几乎回到纯 WikiText 的水平，GSM8K 77.41% 保留了纯自生成提升的 90%。混合比例只试了 1:1。
- **结果偏乐观：** 校准窗口的开头就是评测提示词里的 5 道例题，只是题目来自训练集。换别的任务不能期望同样的提升。
- **只测了 1 次。** 稀疏 kernel 在这个 checkpoint 上没有单独测。之前同一权重下稀疏和稠密的结果一致，这里推测也一致，未验证。

## OBR 校准

- 128 条 WikiText2 train，每条 2048 token，掩码 2:4，逐块级联。
- 模型放 CPU，一次一个块上 GPU。批量 PCG 代替 Cholesky，60 次迭代。
- 单块 36 秒（校准 6 秒，求解 25 秒），36 块共 **1325 秒**。Cholesky 按 16 行抽样外推约 5 小时。
- PCG 40 次迭代时，目标函数比直接解高 0.1%～0.7%（符号修复前后这一对比都成立，因为两者用的是同一个误差向量）。60 次迭代未重新对比。两者都没有达到相对残差 1e-3 的停止条件，每层都用满了迭代次数。
- 单层相对误差平均：INT8 从第 1 块的 0.010 升到中段最高约 0.033，末块 0.014。INT4 是 0.015～0.045。
- 修复后的全程 1298 秒。
- INT4 和 INT8 共用掩码、第一步补偿和级联链，级联走 INT8 的权重。

| 8 | 9.77 | 8.02 | 7.82 | 1.25 | 1.13 |
| 64 | 13.02 | 9.35 | 9.19 | 1.42 | 1.35 |
| 256 | 20.00 | 18.88 | 18.87 | 1.06 | 1.05 |
| 1024 | 72.56 | 73.14 | 71.36 | 1.02 | 1.02 |

## 实现要点

- 文件：`csrc/quantization/w8a8/cutlass/sparse_int8_mm_sm80.cu`、`tools/build_sparse_int8_sm80.sh`、`vllm/model_executor/kernels/linear/scaled_mm/cutlass_sparse.py`。用 `--linear-backend cutlass_sparse` 显式开启，默认路径不变。
- 权重作 A，RowMajor；x 作 B，ColumnMajor。TileShape `<128,128,128>`，WarpShape `<64,64,128>`，指令 m16n8k64。
- 元数据的行重排在 3090 上逐 nibble 测得，见 changelog 坑 48。
- N 必须对齐，kernel 内补齐到 16 的倍数。这使 Decode 的 1 token 按 16 个 token 计算。
- 非 2:4 权重在加载时报错。约束：动态对称激活，M 被 16 整除，K 被 128 整除。
- 数值验证：5 种真实形状 × 7 种 N 加单值 scale，相对误差约 0.17%。真实权重下，稀疏和稠密 kernel 的困惑度 11.99 对 11.97，GSM8K 45.49% 对 44.43%。没有做逐位比较。

## 和原计划的差异

- 用户改了计划：取消仓库外微基准，全部在 vLLM 内测量；测量改为 1 轮，每组合 3 次。OBR checkpoint 的生成仍在 vLLM 外。
- 代码不是 clone 的：仓库私有，服务器上不放凭据，上行只有 3KB/s。服务器从公共镜像取基线 tar 包，比对 Git tree hash 后打补丁。
- 模型第 1 片来自 ModelScope，比对了 HF 的 LFS sha256。
- 没有 tmux，长任务用 `nohup setsid`。
- 数据盘实际是 `/root/rivermind-data`，开始时 49GB。OBR checkpoint 放在系统盘 `/root/obr_ckpt`。

## 未做

- 真正的 s4 × s4 稀疏 kernel：CUTLASS 头文件里有 `int4b_t` 的特化，未编译运行。vLLM 没有动态 4-bit 激活量化。
- KV4：`--kv-cache-dtype turboquant_4bit_nc` 未在 3090 上运行。
- 保护最近 R 个 token：未实现。
- 权重旋转、W4A4KV4：未做。这是论文方法的一部分。
- 提高 2:4 精度的方案：只剪 FFN、跳过敏感层、加旋转。
- `vllm serve` 下带 nsys 和 NVTX 的 trace；3090 上的新 NVTX 标签未实测。
- `ruff`、`pre-commit`、`pytest` 未运行，没有写仓库测试。
