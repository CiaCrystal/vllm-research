# OBR（量化 + 剪枝）在 vLLM 上的可行性与实测

日期：2026-11-06。环境：RTX 5070（SM120），WSL2，Qwen3-0.6B，非 eager。源码未改动。
参考文章：Guo、Li、Benini，*Optimal Brain Restoration for Joint Quantization and Sparsification of LLMs*，ICLR 2026，[arXiv:2509.11177](https://arxiv.org/abs/2509.11177)，[代码](https://github.com/csguoh/OBR)。

## 结论

**不改代码，无法用 OBR 得到 TTFT、TPOT 的提升。** 这里没有 OBR 的性能报告，因为 OBR 没有运行，下面是不可行的依据和可达到的结果。

- 论文的提速依赖专用的 2:4 稀疏 + INT4 CUTLASS kernel。vLLM 里没有这类稀疏线性 kernel，要加就得改源码。
- 权重里的零不会让 vLLM 变快。50% 剪枝后的 INT8 和未剪枝的 INT8 在 TTFT、TPOT、整体耗时上差异都在噪声内。D、F 的差异为 0%～5.8%，方向是持平或略慢。A 的 TTFT 有一项 −8.9%，但另一轮只有 −1.4%，单次范围也完全重叠。
- 显存也没有下降：模型 0.72 GiB、KV 39,424 tokens，与未剪枝完全相同。零仍按稠密方式存储。
- 不做补偿的 50% 幅值剪枝会毁掉模型：GSM8K 从 36.6% 跌到 2.1%，1319 条回答全部触顶。这个结果不代表 OBR 的精度，OBR 正是用来补偿这类误差的。

当前不改代码能达到的最好结果仍是单独量化，FP8 的整体耗时降 15%～25%，INT8 降 11%～27%，见下表。

## 论文的提速从哪里来

| 项目 | 论文 | 本环境 |
| ---- | ---- | ------ |
| 方法 | 旋转 → 剪枝 → 补偿 → 量化，用二阶 Hessian 目标的闭式解计算补偿 | 未运行 |
| 配置 | W4A4KV4 + 50% 稀疏 | 本卡上 W4A8 kernel 不可用（坑 23） |
| 提速 | 摘要：最高 4.72 倍；GEMM 测试：序列长度 4096 时 5.9 倍 | |
| kernel | 用 CUTLASS 实现的 2:4 半结构化稀疏 + INT4 | vLLM 没有 |
| 测试硬件 | A100，权重 4096×4096 | RTX 5070，无法直接外推 |
| 校准 | 128 条 WikiText2，序列长度 2048 | `datasets` 不在 `.venv` |
| 校准耗时 | Llama2-7B 约 2 小时（A100） | Qwen3-0.6B 未测 |

论文未说明 4.72 倍是如何测得的，也未说明 6.4 倍内存节省的计算方法。论文报告的精度测试是常识类任务和 WikiText2 困惑度，没有 GSM8K。这些内容来自对论文页面的读取，未逐表核对。

## 不可行的依据

| 问题 | 依据 |
| ---- | ---- |
| 没有稀疏线性 kernel | `vllm/model_executor/kernels/linear/` 下没有稀疏 GEMM 路径 |
| 稀疏格式被拒绝 | `compressed_tensors.py:298`：带目标的 `sparsity_config` 直接报 `Sparsity support has been removed` |
| 零不提速 | 本次实测，稠密 GEMM 不跳过零 |
| 官方代码不能直接用 | 需要 conda 和 `pip install`，包括 `fast-hadamard-transform`，FlatQuant 还要求 `transformers==4.45.0`，当前环境是 5.22.1，且不能安装。示例和支持列表没有 Qwen3 |

## 实测

**流式请求**（`stream=true`，不带 nsys）。2 轮，路线和配置顺序交替，每组合 15 次，客户端测得。两个数值分别是第 1、2 轮的中位数。批大小 8 的 TTFT 取 8 条都收到首 token 的时刻。

`INT8 + 50%` 不是 OBR：先对 196 个线性权重张量做每张量的 50% 幅值剪枝（零值占比 50.0%～50.1%），再转 INT8，没有补偿。

### TTFT（ms）

| 配置 | bf16 | FP8 | INT8 | INT8 + 50% 剪枝 | 剪枝 vs INT8 |
| ---- | ---- | --- | ---- | --------------- | ------------ |
| A 256×1 | 11.22 / 10.59 | 11.60 / 12.19 | 13.11 / 11.77 | 11.95 / 11.61 | −8.9% / −1.4% |
| D 1024×8 | 157.23 / 156.50 | 106.22 / 105.11（−33%） | 99.55 / 98.79（−37%） | 99.71 / 102.75（−34%～−37%） | +0.2% / +4.0% |
| F 256×8，129 | 40.00 / 39.76 | 28.48 / 27.78（−29%～−30%） | 26.06 / 26.64（−33%～−35%） | 25.57 / 27.05（−32%～−36%） | −1.9% / +1.6% |

A 的单次范围都很宽且重叠（约 10～23 ms），差异不下结论。这说明量化在 A 上没有带来 TTFT 收益。这次不带 nsys，也确认了 CPU 受限不是 nsys 造成的假象，见 `../report.md` 第 8 节。

### TPOT（ms）

| 配置 | bf16 | FP8 | INT8 | INT8 + 50% 剪枝 | 剪枝 vs INT8 |
| ---- | ---- | --- | ---- | --------------- | ------------ |
| A | 2.63 / 2.66 | 2.15 / 2.15（−18%～−19%） | 2.23 / 2.22（−15%～−16%） | 2.24 / 2.27（−15%） | +0.2% / +2.0% |
| D | 4.55 / 4.60 | 3.78 / 3.78（−17%～−18%） | 3.87 / 3.87（−15%～−16%） | 3.88 / 4.03（−12%～−15%） | +0.2% / +4.3% |
| F | 3.55 / 3.57 | 2.77 / 2.76（−22%～−23%） | 2.88 / 2.86（−19%～−20%） | 2.88 / 2.88（−19%） | 0.0% / +0.5% |

### 整体耗时（ms）

| 配置 | bf16 | FP8 | INT8 | INT8 + 50% 剪枝 | 剪枝 vs INT8 |
| ---- | ---- | --- | ---- | --------------- | ------------ |
| A | 95.39 / 95.75 | 80.62 / 80.88（−15.5%） | 84.63 / 82.92（−11%～−13%） | 83.82 / 84.39（−12%） | −0.9% / +1.8% |
| D | 302.93 / 303.54 | 226.72 / 226.48（−25%） | 223.50 / 222.26（−26%～−27%） | 223.68 / 235.18（−23%～−26%） | +0.1% / +5.8% |
| F | 493.78 / 496.86 | 383.04 / 381.81（−22%～−23%） | 394.98 / 393.34（−20%～−21%） | 394.93 / 396.15（−20%） | 0.0% / +0.7% |

D 第 2 轮的 +5.8% 来自一次偏慢的运行（TTFT 最高 113.3 ms），方向也不是提速。第 1 轮同一项为 +0.1%。

### 显存和精度

| 路线 | 模型显存 | KV 容量 | 文件 | gzip 后 | GSM8K | 触顶 256 token |
| ---- | -------- | ------- | ---- | ------- | ----- | ------------ |
| bf16 | 1.12 GiB | 34,816 | 1.40 GiB | | 39.04% / 39.58% | 41 / 35 |
| FP8 | 0.71 GiB | 39,424 | 在线量化 | | 37.76% | 30 |
| INT8 | 0.72 GiB | 39,424 | 0.99 GiB | 0.83 GiB | 36.62% | 123 |
| INT8 + 50% 剪枝 | 0.72 GiB | 39,424 | 0.99 GiB | 0.74 GiB | 2.12% | 1319 |

剪枝只让压缩后的文件小约 11%，这只影响存储和分发，不影响加载后的显存。剪枝模型的输出是循环重复的文本，例如 `24/12 = 24/12 = ...`。配对对比：相对 INT8 失分 474 题、得分 19 题，p < 1e-100。

## 未做或无法确认

- **OBR 没有运行**，所以它在 Qwen3-0.6B 上的精度和校准耗时都未知。
- **精度结果只代表无补偿的幅值剪枝**，掩码也不是论文用的 WANDA。
- **未测试：** 4-bit 权重路线（W4A16）、4-bit KV cache、MXFP8 的流式 TTFT 和 TPOT。
- **论文的提速数字未复现**，也没有在这张卡上验证 2:4 kernel。
- 每组合 2 轮，每轮 15 次。
- 流式客户端是 Python，SSE 解析开销计入了 TTFT，各路线相同。
- 随机 token 的流式输出可能合并少量 chunk，TPOT 用首末 chunk 时间和 `usage` 的 token 数计算，不依赖 chunk 数量。
